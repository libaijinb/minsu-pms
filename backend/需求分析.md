## 1. 项目概述

### 1.1 背景

个人房东或小型民宿经营者通常同时在多个渠道（自营小程序、美团、途家等）接待客人，日常依赖 Excel 和微信群管理房态、排班、收款，存在三个痛点：

1. **超售**：多渠道各卖各的，同一晚被两个客人订走；
2. **服务调度乱**：退房、清洁、维修靠口头传达，漏单和排班冲突频发；
3. **算账糊涂**：佣金、保洁成本、损坏赔付混在一起，月结时对不上账。

PMS 的目标是用一套系统把「房源库存 → 预订 → 服务调度 → 资金结算」完整管起来。

### 1.2 目标

**业务目标**

- 房源以「晚」为粒度进行库存管理，任何渠道不超售；
- 客人从搜索到退房的全程线上化，订单状态全程可追溯；
- 清洁/维修任务自动生成、派工无冲突；
- 按月自动结算，房东应得金额一分不差。

**技术目标（简历向）**

- 落地库存并发防护（条件更新 + 唯一约束双重防线）；
- 落地订单状态机（转换表驱动 + 全流水日志）；
- 落地定时任务调度（Celery beat + 幂等设计）；
- 落地财务事务（Decimal + atomic + 幂等键）。

### 1.3 范围

| | 内容 |
|---|---|
| 本期包含 | 房源管理、日历与价格、预订与订单、入住退房、清洁任务、维修工单、退房查房、评价、结算分账、消息通知、报表统计、用户权限（6 角色） |
| 本期不包含 | 真实 OTA 渠道 API 对接（美团/途家，仅数据模型预留）、智能门锁对接、电子发票、小程序/H5 多端、短信发送（仅站内信 + 邮件控制台） |

### 1.4 名词术语

| 术语 | 定义 |
|---|---|
| 晚（night） | 库存的基本单位。日期 D 表示「D 当晚的住宿权」，非自然日占用 |
| 换客日（turnover day） | 退房日当天上午可安排清洁，下午可供新客入住，即退房日与新客入住日可为同一天 |
| 有效订单 | 状态不属于「已取消」的订单，其占用的晚不可再售 |
| 锁定日期 | 因维修等原因房东主动关闭的日期，客人不可订 |
| ADR | Average Daily Rate，平均每日房价 = 房费收入 ÷ 已售晚数 |
| OCC | Occupancy，出租率 = 已售晚数 ÷ 可售晚数 |
| RevPAR | Revenue per Available Room，每间可售房收入 = 房费收入 ÷ 可售晚数 |
| 渠道 | 订单来源：自营（本系统直订）或第三方平台；不同渠道佣金率不同 |

## 2. 用户角色分析

| 角色 | 描述 | 核心诉求 | 典型场景 |
|---|---|---|---|
| 房东 | 房源所有者，1 人可持有多套房源 | 房源好卖、账算得清、少操心 | 上架房源、定价、看收益报表、处理报修 |
| 运营 | 平台管理人员 | 订单确认、派工调度、查房把关 | 审核房源、确认订单、派保洁、退房查房 |
| 客人 | 预订住宿的人 | 看得到真实房态、下单放心、退改顺畅 | 浏览房源、选日期下单、支付、入住、评价 |
| 保洁 | 清洁服务人员 | 任务清楚、不跑空、时间不撞车 | 查看每日任务列表、标记完成 |
| 维修 | 维修师傅 | 工单明确、地址电话齐全 | 接单、处理、提交维修结果 |
| 财务 | 结算人员 | 月结数据准、分账可追溯 | 生成结算单、执行分账、导出对账表 |

## 3. 端到端业务流程

### 3.1 主流程（Happy Path）

```
① 房东创建房源并提交审核
② 运营审核通过，房源上架，系统生成未来 365 天日历
③ 房东配置基础价与价格规则（周末价/节假日/连住折扣/清洁费）
④ 客人在可订日期区间内下单（占房：可订 → 已订）
⑤ 客人支付（支付超时 15 分钟未付自动取消，释放日历）
⑥ 房东/运营确认订单（24 小时未确认自动确认）
⑦ 客人到店，运营办理入住登记（登记实名信息、收取押金）
⑧ 客人退房，订单转「已退房」，系统同时触发：
      ├─ 生成清洁任务（默认次日上午时段）
      ├─ 生成查房任务（运营）
      └─ 自退房日晚起释放为「可订」（换客日规则，见 BR-CAL-01）
⑨ 保洁完成清洁 → 运营复核 → 任务完成
⑩ 运营查房：无损坏 → 全额退押金；有损坏 → 定损 → 扣押金 → 生成维修工单
⑪ 客人与房东双向评价
⑫ 每月 1 日，系统按房东 + 上月周期生成结算单并分账
```

### 3.2 关键子流程

**取消流程**：客人/房东发起取消 → 按取消政策计算退款 → 订单转「已取消」→ 释放日历 → 已收押金/房款原路退回 → 发通知。

**维修流程**：报修（客人/房东/查房定损）→ 运营派工 → 维修处理 → 房东/运营验收 → 工单完成；维修期间相关日期置「已锁定」。

## 4. 功能需求

编号规则：`FR-<模块码>-<序号>`，优先级 **P0 必须 / P1 重要 / P2 增强**。

### 4.1 房源管理（LST）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-LST-01 | 创建房源 | 作为房东，我希望录入房源信息（名称、房型、面积、可住人数、设施、床位、位置、图片），以便客人了解房源 | P0 |
| FR-LST-02 | 编辑房源 | 作为房东，我希望随时修改房源信息与图片，以便信息保持准确 | P0 |
| FR-LST-03 | 提交审核 | 作为房东，我希望提交房源进入审核，以便房源能上架销售 | P0 |
| FR-LST-04 | 审核房源 | 作为运营，我希望审核房东提交的房源（通过/驳回并填写理由），以便控制平台房源质量 | P0 |
| FR-LST-05 | 上下架 | 作为房东/运营，我希望上架或下架房源，以便灵活控制销售状态 | P0 |
| FR-LST-06 | 房源列表与详情 | 作为客人，我希望按城市/价格/人数筛选并查看房源详情，以便决定预订哪间 | P0 |
| FR-LST-07 | 评分聚合 | 作为客人，我希望看到房源历史评分，以便判断口碑 | P2 |

**业务规则**

- BR-LST-01：房源状态机：`草稿 → 审核中 → 已上架 ⇄ 已下架`；审核驳回回到「草稿」。
- BR-LST-02：仅「已上架」房源对客人可见、可被预订。
- BR-LST-03：存在**未来的有效订单**（已确认/已入住）的房源不允许下架，需先处理订单。
- BR-LST-04：房东只能查看/操作自己的房源（数据范围隔离）；运营可操作全部。
- BR-LST-05：单房源至少 1 张图片，最多 9 张。

### 4.2 日历与价格管理（CAL）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-CAL-01 | 日历生成 | 作为系统，我希望在房源上架时生成未来 365 天日历，以便支撑查询与占房 | P0 |
| FR-CAL-02 | 日历查询 | 作为客人，我希望看到所选日期区间内每晚的价格与可订状态，以便决定是否下单 | P0 |
| FR-CAL-03 | 批量改价 | 作为房东，我希望按日期区间批量设置价格，以便应对淡旺季 | P0 |
| FR-CAL-04 | 关闭/打开日期 | 作为房东，我希望关闭某些日期（自留、维修）或重新打开，以便灵活管理库存 | P0 |
| FR-CAL-05 | 价格规则 | 作为房东，我希望配置基础价、周末价、节假日价、连住折扣，以便定价自动化 | P1 |
| FR-CAL-06 | 价格日历视图 | 作为房东，我希望以日历视图总览整月房价与占用，以便一目了然 | P1 |

**业务规则**

- BR-CAL-01：日历单位是「晚」。订单入住日 D1 至退房日 D2，占用区间 `[D1, D2)` 内的所有晚；D2 当天可被其他订单作为入住日（换客日）。
- BR-CAL-02：日历状态：`可订 / 已订 / 已锁定 / 已关闭`。仅「可订」的晚可被下单占用。
- BR-CAL-03：最终晚价计算优先级：**指定日期价 > 节假日价 > 周末价 > 基础价**；同级不叠加，取最高优先级。
- BR-CAL-04：连住折扣按订单总晚数匹配门槛（住 ≥7 晚 9 折，≥30 晚 85 折），只取一档，不叠加。
- BR-CAL-05：订单金额 = Σ 每晚最终价 × 晚数 − 连住折扣 + 清洁费（一次性）+ 平台服务费（按渠道比例，客人承担或房东承担二选一，默认房东承担）。
- BR-CAL-06：客人下单时看到的金额必须**快照**进订单（房价明细 JSON + 总金额），后续改价不影响历史订单。
- BR-CAL-07：日历采用「懒生成 + 定时补漏」策略：首次查询到某日期时若无记录则按当前规则生成；每日凌晨任务补齐未来 365 天。
- BR-CAL-08：已订/已锁定的晚不允许批量改价直接覆盖，改价仅作用于「可订」晚（或弹出确认）。

### 4.3 预订与订单管理（ORD）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-ORD-01 | 创建订单 | 作为客人，我希望选择日期区间并提交预订，以便锁定心仪房源 | P0 |
| FR-ORD-02 | 占房防超售 | 作为系统，我希望保证同一晚只能被一单有效占用，以便绝不超售 | P0 |
| FR-ORD-03 | 模拟支付 | 作为客人，我希望在线支付订单，以便完成预订 | P0 |
| FR-ORD-04 | 支付超时取消 | 作为系统，我希望 15 分钟未支付的订单自动取消并释放日历，以便库存不浪费 | P0 |
| FR-ORD-05 | 确认订单 | 作为房东/运营，我希望确认客人的预订，以便客人安心等待入住 | P0 |
| FR-ORD-06 | 取消订单 | 作为客人/房东/运营，我希望按政策取消订单并自动计算退款 | P0 |
| FR-ORD-07 | 订单列表与详情 | 作为各类角色，我希望按状态/时间/房源筛选订单并查看全流水 | P0 |
| FR-ORD-08 | 订单金额明细 | 作为客人/房东，我希望看到金额构成（房费/折扣/清洁费/服务费），以便花钱明白 | P1 |
| FR-ORD-09 | 未入住（no-show）处理 | 作为运营，我希望标记客人未入住并按政策扣款 | P2 |

**业务规则**

- BR-ORD-01：订单状态机见第 5 章。
- BR-ORD-02：占房采用「条件更新 + 唯一约束」双重防线：先执行 `UPDATE calendar SET status='已订' WHERE listing_id=? AND date=? AND status='可订'`，影响行数不足即冲突回滚；数据库层另有 `(listing_id, date)` 唯一约束兜底。占房与建订单在同一事务内。
- BR-ORD-03：创建订单时校验：日期区间合法（D1 < D2、D1 ≥ 明天）、区间内全部晚可订、可住人数 ≥ 入住人数。
- BR-ORD-04：取消政策：入住前 3 天（含）免费取消全额退；入住前 3 天内取消扣首晚房费 50%；no-show 全扣。
- BR-ORD-05：订单支付成功后进入「待确认」；房东/运营 24 小时未确认则**自动确认**并通知客人（避免房东不操作坑客人）。
- BR-ORD-06：已确认订单取消除按 BR-ORD-04 退款外，若距入住不足 3 天需房东同意（运营可强制）。
- BR-ORD-07：订单每次状态转换必须写一条 `order_status_log`（操作人、时间、前后状态、备注）。
- BR-ORD-08：订单号规则 `PM` + 年月日 + 6 位随机数，全局唯一。

### 4.4 入住退房管理（CIO）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-CIO-01 | 入住登记 | 作为运营，我希望登记入住人实名信息与同住人，以便合规管理 | P0 |
| FR-CIO-02 | 收取押金 | 作为运营，我希望记录押金收取（金额、方式），以便退房时结算 | P0 |
| FR-CIO-03 | 办理退房 | 作为运营，我希望一键退房，系统自动完成下游动作 | P0 |
| FR-CIO-04 | 押金处理 | 作为运营，我希望按查房结果退还或部分扣减押金 | P0 |

**业务规则**

- BR-CIO-01：仅「已确认」且入住日在当天或之前的订单可办理入住；入住后订单转「已入住」并记录实际入住时间。
- BR-CIO-02：退房动作必须触发三件事（同事务或同任务链）：① 生成清洁任务 ② 生成查房任务 ③ 订单转「已退房」。任一失败需可重试且幂等。
- BR-CIO-03：押金状态：`未收 / 已收 / 已全额退 / 已部分扣`；扣减金额 = 查房定损总额，逐条工单/定损记录可追溯。
- BR-CIO-04：退房后，退房日之后的已占用日期全部释放为「可订」（退房日当晚起可再售）。

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-CLN-01 | 自动生成任务 | 作为系统，我希望客人退房后自动生成清洁任务，以便不漏单 | P0 |
| FR-CLN-02 | 手动创建任务 | 作为运营，我希望为深度保洁等场景手动建任务 | P1 |
| FR-CLN-03 | 派工 | 作为运营，我希望把任务派给具体保洁并指定时段，以便责任到人 | P0 |
| FR-CLN-04 | 冲突检测 | 作为系统，我希望阻止同一保洁同一时段被派两单，以便不跑空 | P0 |
| FR-CLN-05 | 我的任务 | 作为保洁，我希望看到今日/本周任务列表（地址、时段、特殊要求），以便按序执行 | P0 |
| FR-CLN-06 | 完成与复核 | 作为保洁，我希望标记完成并上传照片；作为运营，我希望复核后关单 | P1 |

**业务规则**

- BR-CLN-01：任务状态：`待派工 → 已派工 → 进行中 → 待复核 → 已完成`。
- BR-CLN-02：默认时段：退房日次日上午（保证下午新客入住前完成）；运营可改派下午。
- BR-CLN-03：派工冲突用 `(cleaner_id, task_date, slot)` 唯一约束物理拦截，应用层同时预检给出友好提示。
- BR-CLN-04：任务与订单一对一（退房触发），`order_id` 唯一约束保证 beat 重复执行不重复生成（幂等）。
- BR-CLN-05：保洁完成需上传至少 1 张照片；运营复核通过才置「已完成」。

| FR-REP-02 | 派工 | 作为运营，我希望把工单派给维修师傅，以便跟进处理 | P1 |

| FR-REP-04 | 关联日期锁定 | 作为系统，我希望维修期间自动锁定相关晚的日历，以便不再售卖 | P1 |

**业务规则**

- BR-REP-01：工单状态：`待派工 → 已派工 → 处理中 → 待验收 → 已完成 / 已关闭（不予维修）`。
- BR-REP-02：查房定损损坏项自动生成维修工单，来源标记「查房定损」，定损金额关联押金扣减。
- BR-REP-03：维修中日期置「已锁定」；完工验收后由运营决定是否解锁恢复可订。

### 4.7 退房查房管理（INS）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-INS-01 | 查房任务单 | 作为运营，我希望收到退房查房任务并按清单逐项检查 | P0 |
| FR-INS-02 | 记录检查结果 | 作为运营，我希望逐项记录正常/异常并上传照片、填写定损金额 | P0 |
| FR-INS-03 | 定损处理 | 作为运营/房东，我希望对定损金额确认或申诉，以便公平扣款 | P1 |

**业务规则**

- BR-INS-01：检查项模板化：卫生（厨房/卫生间/卧室）、物品完好（电器/家具/布草）、能耗读数（水表/电表）。
- BR-INS-02：定损金额 ≥ 500 元需房东二次确认；不足则运营直接定损。
- BR-INS-03：查房结论：`合格 → 全额退押金`；`不合格 → 按定损扣减，逐项关联维修工单`。
- BR-INS-04：查房记录是押金扣减与结算扣款的唯一依据，必须留照片与操作人。

### 4.8 评价管理（REV）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-REV-01 | 客人评房源 | 作为客人，我希望对住宿体验评分和文字/图片评价 | P2 |
| FR-REV-02 | 房东评客人 | 作为房东，我希望评价客人的守约与卫生习惯 | P2 |
| FR-REV-03 | 房东回复 | 作为房东，我希望回复客人评价 | P2 |
| FR-REV-04 | 评分聚合 | 作为系统，我希望把房源均分回写房源表 | P2 |

**业务规则**

- BR-REV-01：双向评价，退房后 14 天内可评，逾期关闭。
- BR-REV-02：一方评价后另一方 14 天内未评则关闭，不互相公开（避免差评要挟）。
- BR-REV-03：评分 1-5 星，均分保留 1 位小数；房东回复后不可修改。

### 4.9 结算与分账（STL）

| 编号 | 功能 | 用户故事 | 优先级 |
|---|---|---|---|
| FR-STL-01 | 月结任务 | 作为系统，我希望每月 1 日自动为每个房东生成上月结算单 | P1 |
| FR-STL-02 | 结算单明细 | 作为财务/房东，我希望看到订单收入、佣金、成本、应付明细，以便对账 | P1 |
| FR-STL-03 | 执行分账 | 作为财务，我希望一键分账并记录每笔分账状态 | P1 |
| FR-STL-04 | 分账重试 | 作为财务，我希望对失败的分账记录重试，以便不卡死月结 | P1 |
| FR-STL-05 | 对账导出 | 作为财务，我希望导出周期对账表（Excel），以便线下核查 | P2 |

**业务规则**

- BR-STL-01：结算公式：`房东应得 = Σ订单实付 − 平台佣金(按渠道率) − 保洁成本(按完成的任务单计) − 损坏赔付(未覆盖押金部分)`。
- BR-STL-02：渠道佣金率：自营 8%、美团 15%、途家 12%（可配置）。
- BR-STL-03：结算周期：自然月，每月 1 日 02:00 执行，只结算状态为「已退房」的订单。
- BR-STL-04：幂等：`(landlord_id, period)` 唯一约束 + 结算前批量校验订单状态，重复执行不产生重复结算单。
- BR-STL-05：结算单状态：`待分账 → 分账中 → 已分账 → 分账失败(可重试)`；分账记录逐笔留状态与流水号。
- BR-STL-06：结算动作（订单批量转「已结算」+ 生成结算单 + 生成分账记录）必须在同一数据库事务中；金额一律 Decimal(10,2)。

| FR-MSG-02 | 邮件（控制台） | P2 | 开发期用 Django console 邮件后端 |

### 4.11 报表统计（RPT）

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|
| FR-RPT-01 | 经营概览 | P1 | OCC / ADR / RevPAR 趋势图（按月） |
| FR-RPT-02 | 渠道占比 | P1 | 订单数/收入按渠道饼图 |
| FR-RPT-03 | 任务看板 | P1 | 清洁/维修完成率、保洁工作量排名 |
| FR-RPT-04 | 对账报表 | P2 | 结算周期明细导出 |

**业务规则**

- BR-RPT-01：OCC = 已售晚数 ÷ 可售晚数（可售晚数 = 日历中非「已关闭」的晚）；ADR = 房费收入 ÷ 已售晚数；RevPAR = 房费收入 ÷ 可售晚数。
- BR-RPT-02：房东看板只看自己房源；运营/财务看全平台。

| 编号 | 功能 | 优先级 | 说明 |
|---|---|---|---|

| FR-USR-04 | 数据范围隔离 | P0 | 房东看自己的房源与订单，客人看自己的订单，保洁看自己的任务 |

**业务规则**

- BR-USR-01：角色决定可访问的接口，数据范围决定可见的数据行，两层叠加。
- BR-USR-02：保洁/维修/财务账号由运营创建并分配角色，不支持自助注册。
- BR-USR-03：一个用户可同时拥有多个角色（如既是房东又是客人），权限取并集。

## 5. 订单状态机

### 5.1 状态定义

| 状态 | 含义 | 终态 |
|---|---|---|
| 待支付 | 已创建订单，未支付 | 否 |
| 待确认 | 已支付，等待房东/运营确认 | 否 |
| 已确认 | 预订成立，等待入住 | 否 |
| 已入住 | 已办理入住登记 | 否 |
| 已退房 | 已办理退房，服务/查房进行中 | 否 |
| 争议中 | 存在未处理的损坏纠纷 | 否 |
| 已取消 | 订单取消（退款按政策） | 是 |
| 已结算 | 已完成月结合账 | 是 |

### 5.2 转换表

| 当前状态 | 触发动作 | 目标状态 | 执行角色 | 副作用 |
|---|---|---|---|---|
| — | 创建订单 | 待支付 | 客人 | 占房（事务内）、金额快照、通知房东待确认预备 |
| 待支付 | 支付成功 | 待确认 | 系统 | 记录支付流水、通知房东/运营 |
| 待支付 | 支付超时/客人取消 | 已取消 | 系统/客人 | 释放日历、通知 |
| 待确认 | 确认 | 已确认 | 房东/运营 | 通知客人 |
| 待确认 | 24h 超时 | 已确认 | 系统（定时） | 自动确认、通知双方 |
| 待确认 | 拒单/取消 | 已取消 | 房东/运营 | 全额退款、释放日历 |
| 已确认 | 到店登记 | 已入住 | 运营 | 写入住登记、记录押金 |
| 已确认 | 取消 | 已取消 | 客人/房东/运营 | 按政策退款、释放日历 |
| 已入住 | 退房 | 已退房 | 运营 | 生成清洁+查房任务、释放后续日期、通知 |
| 已退房 | 产生纠纷 | 争议中 | 运营 | 生成维修工单、锁定日期 |
| 争议中 | 纠纷处理完 | 已退房 | 运营 | 继续结算流程 |
| 已退房 | 月结 | 已结算 | 系统（定时） | 生成结算单+分账记录（事务） |
| 已退房 | no-show 标记 | 已取消 | 运营 | 全扣款、释放日历 |

### 5.3 实现约束

- 转换表驱动：应用层只维护「当前状态 × 动作 → 目标状态」合法映射，非法转换直接拒绝；
- 每次转换必写 `order_status_log`（前后状态、操作人、时间、备注）；
- 副作用（通知、任务生成、释放日历）集中在转换处理器中显式列出，禁止散落 if-else。

| User | username, password, phone, role(s) | 1:N Listing / Order / Task |
| Listing | owner, title, type, area, max_guests, address, status, rating | N:1 User |
| Calendar | listing, date, status, price, lock_reason | N:1 Listing；unique(listing, date) |

| Notification | user, event, title, content, is_read | N:1 User |

### 6.2 关键设计说明

- **金额字段**：一律 `DecimalField(max_digits=10, decimal_places=2)`；订单金额明细以 JSON 快照存储（房价明细 + 各项费用），保证历史订单不受后续调价影响。
- **日期字段**：日历与订单用 `DateField`（日期粒度）；时间戳统一 UTC 存储、东八区展示。
- **并发字段**：Calendar 加 `(listing_id, date)` 唯一约束；CleaningTask 加 `(cleaner_id, task_date, slot)` 与 `(order_id)` 唯一约束；Settlement 加 `(landlord_id, period)` 唯一约束——三个唯一约束分别守住超售、派工冲突、重复结算。

### 7.2 安全

| 编号 | 需求 |
|---|---|
| NFR-SEC-01 | 全站 JWT 认证，access/refresh 双 token，401 统一拦截登出 |
| NFR-SEC-02 | RBAC + 数据范围双层权限；对象级校验（非本人数据返回 404 而非 403，避免暴露存在性） |
| NFR-SEC-03 | 密码 Django 默认 PBKDF2 哈希；敏感操作（支付、取消、分账）记录操作日志 |
| NFR-SEC-04 | 支付回调验签 + 幂等（同一 trade_no 重复回调只入账一次） |
| NFR-SEC-05 | 金额计算禁用 float；防止并发改价覆盖已下单金额（快照机制） |

### 7.3 可用性与可维护性

| 编号 | 需求 |
|---|---|
| NFR-AVL-01 | 定时任务（支付超时、自动确认、月结）全部幂等，可安全重复执行 |
| NFR-AVL-02 | 关键业务动作留流水：订单状态、押金、结算、分账四类日志可追溯 |

| NFR-AVL-04 | 异常统一由 DRF 异常处理返回结构化错误（字段级中文提示） |

## 9. 需求优先级与分期

> 优先级（P0/P1/P2）表示**重要性**；阶段（一/二/三期）表示**时间排期**，两者不完全等同——例如报表功能是一期主链路稳定后再做的增强，虽标 P1 仍排入三期。

| 阶段 | 周期 | 内容 | 验收标准 |
|---|---|---|---|
| 一期 | 2 周 | LST + CAL + ORD + CIO + USR | 客人能选日期下单支付，房东能确认，运营能登记入住/退房；压测 50 并发零超售 |
| 二期 | 1.5 周 | CLN + REP + INS + MSG | 退房自动生成清洁+查房任务，派工冲突被拦截，查房定损联动押金 |
| 三期 | 1 周 | STL + RPT + REV | 月结自动生成结算单并分账，看板三指标图表可展示，双向评价可用 |

**P0 清单**：FR-LST-01~06、FR-CAL-01~04、FR-ORD-01~07、FR-CIO-01~04、FR-CLN-01~05、FR-INS-01~02、FR-USR-01、FR-USR-03、FR-USR-04。
**P1 清单**：FR-CAL-05~06、FR-ORD-08、FR-CLN-06、FR-REP-01~04、FR-INS-03、FR-STL-01~04、FR-MSG-01、FR-RPT-01~03、FR-USR-02。
**P2 清单**：FR-LST-07、FR-ORD-09、FR-REV-01~04、FR-STL-05、FR-RPT-04、FR-MSG-02。
